# BET-003 design: authentication and account management

## Scope and security

Implement [BET-003](BET-003.md), with [ADR-007](../adr/ADR-007.md) superseding ADR-001. The use-case diagram assigns login to users and account management to admins; reservation customers remain separate from login accounts. The class diagram includes an enabled flag; the user explicitly chose to omit it in favor of soft deletion. Preserve ADR-002's optional court/surface seeding and ADR-006's public documentation.

Restore Spring Security and use stateless HTTP security. Disable session-based authentication and CSRF for the API; Basic credentials are accepted only by `POST /api/auth/login`. JWTs use `Authorization: Bearer <token>` on protected requests and refresh; login and refresh return `Authorization: Bearer <token>` and no credentials in the body. Public documentation includes the configured OpenAPI and Swagger UI paths and their required assets. Deny other unrecognized requests by default rather than exposing additional endpoints. Secure all account operations for ADMIN before permitting read operations for USER or ADMIN, then permit reservation creation to both roles and remaining application operations to ADMIN only. Authentication failures return 401 with a Basic challenge on login and a Bearer challenge on bearer-protected requests, including refresh; authenticated authorization failures return 403.

Use a vetted JWT library and a configured HMAC signing secret. Require an externally provided sufficiently strong secret and fail startup on missing or invalid configuration; supply test-only secrets in tests. Validate signature, algorithm, required claims and expiry. Configure positive token lifetime and refresh window, defaulting to one hour and 15 minutes; reject an invalid window larger than the lifetime. Refresh requires a valid bearer token and succeeds when remaining lifetime is at most the refresh window; otherwise return 403. Expired, malformed, revoked or missing tokens return 401.

JWT subject is the immutable account ID, with a credential version claim. For each request, load the account and use its current role; reject deleted or absent accounts and mismatched credential versions. Increment the version transactionally on password changes. For PUT, compare the supplied password against the current BCrypt hash; retain the hash and version when unchanged. Login must verify the password and capture the version from the same consistent account snapshot, so a concurrent password change cannot issue a valid token from old credentials with a new version. Refresh uses the same validation. A username change does not invalidate tokens. BCrypt hashes passwords; never return or log credentials or hashes.

## Account API and persistence

Add an account feature slice with manual EntityManager DAO, entity, DTOs, service and controller. UserAccount extends BaseEntity with soft deletion and an associated Role entity with USER or ADMIN role type; add a credential version. Omit the diagram's enabled flag as explicitly requested. Store a unique active username, BCrypt hash and role. Use Liquibase for schema and a separate unconditional seed changeset with the hashed `admin` / `admin` ADMIN account, independent of `SEED_DATA_ENABLED`; keep Hibernate validation. Document the seed's development-only credentials and H2's in-memory lifetime.

Provide `GET /api/accounts`, `GET /api/accounts/{id}`, `POST /api/accounts`, `PUT /api/accounts/{id}` and `DELETE /api/accounts/{id}`. POST and PUT require username, password and role; PUT fully replaces these fields. Responses contain ID, username and role only. Trim usernames, require 1–50 characters, reject `:` because Basic authentication uses it as a separator, and compare usernames case-sensitively, including on login; reject blank usernames and passwords. Require passwords of 1–72 UTF-8 bytes, without trimming; accept only USER and ADMIN roles. Deleted accounts are excluded from normal lookups and their usernames may be reused; enforce active username uniqueness in the database. Return 201 with Location on creation, 200 for reads and update, 204 on deletion, 400 for invalid input, 404 for missing or deleted accounts and 409 for duplicate usernames or an attempt to delete or demote the last Admin. Serialize account mutations using the existing transactional mutation guard so concurrent admin changes cannot bypass the last-admin invariant.

## Documentation and verification

Document Basic login, bearer authentication, refresh, success Authorization headers, security schemes and relevant 401/403 responses across affected OpenAPI operations, without requiring authentication to retrieve the specification or UI. Update README with API usage and configuration. Add unit tests for validation, credential versioning, role and refresh rules; integration tests for security filters, challenges, persistence, migrations, uniqueness, concurrent last-admin operations and concurrent login/password changes; and end-to-end tests for login, User/Admin permissions, refresh and account changes through the running application. Cover same-password replacement, refresh immediately outside and exactly at the window and immediately before and at expiry, invalid tokens, version mismatch and deletion. Update existing HTTP tests to authenticate where needed; test anonymous OpenAPI, Swagger UI and supporting assets, and deny access to the H2 console if enabled. Run `./mvnw clean verify` with Java 25 and report discovery and any omitted levels.
