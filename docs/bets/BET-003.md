# BET-003: Authentication and account management

## Desired outcome

Protect the reservation API with role-based authentication and enable administrators to manage login accounts.

## Problem

API operations currently lack authentication and role-based access control, and there is no account management.

## Value

Users can make reservations while administrators control accounts and administrative operations.

## Scope

- In scope: Database-backed accounts, administrator-only account management, Basic login, JWT authentication and refresh, and role-based authorization.
- Out of scope: Public registration and deployment hardening.
- Constraints: Keep the feature simple; OpenAPI and Swagger UI are publicly accessible. The initial admin seed is independent of court and surface seeding.

## Acceptance criteria

- Admins can list, retrieve, create, update and soft-delete accounts, including usernames, passwords and roles; responses never expose password hashes. Users cannot manage accounts. The last Admin cannot be deleted or demoted.
- Usernames containing `:` are rejected because HTTP Basic authentication uses it to separate the username and password.
- A migration creates an initial Admin with username `admin` and BCrypt-hashed password `admin`.
- `POST /api/auth/login` authenticates using HTTP Basic and returns a JWT in the Authorization response header.
- Users can access read operations and create reservations; Admins can access all operations. Protected operations require a valid JWT; OpenAPI and Swagger UI are public.
- JWT signing secret, lifetime and refresh window are configurable; the lifetime defaults to one hour and the refresh window to the final 15 minutes. `POST /api/auth/refresh` returns a new JWT in the Authorization header only for an unexpired token in that window.
- Missing, invalid or expired authentication returns 401; insufficient permissions or refresh outside the window returns 403.
- Account deletion and password changes invalidate existing tokens; role changes apply immediately.
