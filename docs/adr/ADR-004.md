# ADR-004: Serialize reservation mutations with the existing guard

Status: Accepted | Date: 2026-11-17 | Supersedes: None

## Context

[BET-002](../bets/BET-002.md) requires atomic customer creation, nonoverlapping court reservations under concurrency, stable recorded prices, and prevention of court deletion while a booking is ongoing or upcoming. A check followed by an unprotected write can race. The existing court and surface design uses a transactional database guard to serialize mutations; a more granular locking scheme is an alternative but adds ordering and coordination complexity. The class diagram associates each reservation with one court and one customer. ADR-001 leaves the API unauthenticated; ADR-002's seed behavior remains unchanged.

## Decision

Implement reservation and customer persistence and API behavior described in [the BET-002 design](../bets/BET-002-design.md). Extend the existing database mutation guard to reservation writes and customer creation, holding it in the same transaction across validation and persistence, and continue using it for court and surface mutations. Use a unique customer phone constraint as an additional backstop, store the reservation's calculated price, and check court deletion against ongoing and future reservations while holding the guard. This reuses the existing simple H2 concurrency mechanism and keeps these related checks atomic.

## Consequences

All guarded mutations serialize, limiting write throughput but simplifying conflict and lifecycle guarantees. Every relevant write path must acquire the guard before reading mutable state and keep it until transaction completion. Database migrations, service and HTTP tests, concurrent integration tests, and end-to-end verification are required. The API exposes customer information without authentication under ADR-001 and must not be exposed to untrusted users until security is designed and implemented.
