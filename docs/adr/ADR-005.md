# ADR-005: Make reservation listing filters optional

Status: Accepted | Date: 2026-11-17 | Supersedes: None

## Context

[BET-002](../bets/BET-002.md) now also requires an unfiltered reservation listing and an optional future-only filter for both all-reservation and phone-specific listings. The approved design previously required a phone number for the existing collection endpoint. A separate all-reservations endpoint is an alternative, but would duplicate the same listing and filter semantics. ADR-004 remains the decision for reservation mutations and concurrency; ADR-001's unauthenticated-access caveat remains in force.

## Decision

Use `GET /api/reservations` for both listings: omit `phoneNumber` for all reservations or provide it to restrict results, and optionally set `futureOnly=true` for either. Keep the default as false, reject an explicitly blank phone number, and order active results by creation time descending then ID descending, as detailed in the updated [BET-002 design](../bets/BET-002-design.md).

## Consequences

Existing phone-filtered requests remain supported, while the endpoint now exposes the entire active reservation collection when the phone filter is omitted. Customer names and phone numbers remain unauthenticated under ADR-001, so the API must not be exposed to untrusted users. Add integration and HTTP tests for all filter combinations, ordering, invalid input and deletion; run the full verification and independent review before Human Gate 2.
