# ADR-007: Secure the API with database accounts and JWTs

Status: Accepted | Date: 2026-11-17 | Supersedes: ADR-001

## Context

[BET-003](../bets/BET-003.md) requires role-based access, account management, Basic login and JWT refresh. ADR-001 temporarily disabled security pending this work. Configuration-only accounts would not satisfy database-backed account management. The use-case diagram assigns account management to admins; reservation customers remain separate from login accounts. ADR-002 retains independent optional court and surface seeding; ADR-006 keeps API documentation public.

## Decision

Restore Spring Security and implement stateless JWT-based authorization backed by database accounts, as detailed in the [BET-003 design](../bets/BET-003-design.md). Authenticate Basic credentials only at login, issue signed bearer tokens, and load current account state on each protected request. Use a credential version to invalidate tokens after password changes, and soft-delete accounts without a separate enabled flag, as explicitly requested despite the class diagram. Restrict account management to admins and prevent deleting or demoting the last admin with transactional serialization. Add a separate unconditional Liquibase admin seed, configurable signing secret, token lifetime and refresh window, and publicly accessible OpenAPI and Swagger UI.

## Consequences

Every authenticated request incurs an account lookup; role changes, deletion and password changes take effect without waiting for token expiry. The default admin credentials are intentionally insecure and only appropriate for development; the signing secret must be configured. Account mutation serialization trades throughput for a simple last-admin invariant. Existing API clients and tests must authenticate, and OpenAPI security documentation and unit, integration and end-to-end coverage must be updated. Human design approval and independent review remain required.
